# 第六轮功能复核：主循环卡顿与快速迫降

基线：第五轮文档提交 `b6680e0`。本轮审查其后构建开关、飞行日志、IMU 等待、Web 停机快通道、网页传输与本地序列改动；重点是主循环延迟和迫降在拥塞时的可达性。工作区原有未提交的台架记录、构建镜像与验证文档保留原样，本轮结论只对应本轮源码树及明确指出的既有记录。

## 按功能倒序复核

| 功能 | 本轮发现与处理 | 剩余风险 |
| --- | --- | --- |
| 本地路线回放与控制入口 | 录制输入回放不重复限速；按最新要求删除“停止并下降”和“自稳手动启动”按钮、`/route/stop`、`/route/start`，仅保留上锁上传、AUTO 启动、手动接管及遥控器独立迫降。 | AUTO 路线及迫降缺少对应最新镜像的完整板端日志。 |
| Web 控制和快速迫降 | 端口 82 使用独立监听与非阻塞请求行读取；上锁、急停、迫降进入优先级队列（急停 > 上锁 > 迫降），由主循环在 IMU 前消费。三种动作都要求随机停机凭证，飞行中重新领取控制租约也要求原凭证；普通 Web 按钮路径保留凭证验证。 | 没有对当前源码镜像做实际浏览器到设备的端到端延迟测量；4 ms 请求行窗口下需用实际 Wi-Fi 验证。 |
| 主循环详细阶段计时 | 默认关闭逐阶段监控以减轻 1 kHz 热路径开销；诊断构建显式打开。修正关闭监控时 host 编译失败，以及慢循环追踪/跨重启留存被误关的问题；无详细阶段时以 `unaccounted` 保存整轮耗时。 | 默认镜像无法对每一阶段直接归因；需要诊断镜像复现。 |
| 飞行日志与网页传输 | 提供可关闭飞行日志的构建开关，关闭时减少热路径采样；默认仍开启飞行日志。HTML 分块发送降低主 Web 服务占用。关闭飞行日志时仍逐帧采集下降校准样本。 | 网页大传输仍需板端实测确认最坏 HTTP 占用。 |
| IMU 等待与控制 | 已有约 1.6–1.7 ms 事件多由约 1.0 ms 的 IMU 等待主导；也存在由 RC/Web 与控制阶段占用主导的事件。未据此盲改 `waitForData(5)`。 | 历史约 50 ms 事件需要同一 loop sequence 的 IMU、任务切换、IPC、重启原因数据才能归因。 |
| 内存与构建 | 缩小最近事件 ring，为 ESP32-D 详细阶段和任务切换构建保留 DRAM 空间；最坏记录及 RTC 留存独立保存。 | 缩小后最近事件保留窗口略短。 |

## 证据边界

- `python3 tests/run_host_tests.py` 通过，覆盖默认与详细阶段监控两种控制状态构建，以及快速动作解析与优先级、租约覆盖和已删除路线端点的准入策略。页面三段 JavaScript 均通过 `node --check`；`git diff --check` 通过。
- ESP32-D 默认、详细阶段监控、完整任务切换追踪构建均通过；固件 Flash 分别为 1,352,375、1,353,559、1,357,775 B，静态 RAM 分别为 124,548、124,564、124,484 B。
- 新路线采集目录中的 flight log 曾在实际回放前冻结，不能作为回放阶段卡顿归因证据。一次 53.596 ms 行发生于已上锁状态，不能称为 armed 卡顿；已见的回放相关 worst trace 最大约 2.093 ms。
- 本轮不刷写、不解锁、不驱动电机。固件编译证明可构建，不能代替板端时延或带载飞行验收。
